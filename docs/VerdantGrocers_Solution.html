Controlled Test

1. Business Context

Verdant Grocers operates 140 stores [VGI-F01] across three states [VGI-F02]. Today, store managers reorder from an overnight report, so a sell-out at 10 AM [VGI-F15] is not visible to replenishment until the next morning [VGI-F15].

The event path already exists: each store's point-of-sale terminals emit a transaction event per basket [VGI-F03], and those events reach an on-premises message broker today [VGI-F04]. The chain sees roughly 900,000 basket events per day [VGI-F05] with a pronounced weekday-evening peak [VGI-F05].

Phase 2 adds the missing facts that materially change the architecture: zero basket-event loss [VGI-F16] (given), a recoverable gap requirement [VGI-F18], a cloud run-rate ceiling of USD 8,000 per month [VGI-F19], and a PCI DSS boundary that keeps cardholder data out of the analytics platform [VGI-F20] [VGI-F21].

3. Functional & Quality Requirements

Functional Requirements

  • The system must consume basket-sale events from the existing flow.
  • The system must update store-level stock positions from those sales.
  • The system must expose an operational inventory view for merchandising and replenishment.
  • The system must continue feeding the overnight finance warehouse.
  • The system must keep any reconciliation gap recoverable, not merely detectable [VGI-F18].
  • The system must remove or tokenise cardholder data before events leave the store network [VGI-F21].

Quality Attributes

  • Freshness: stock positions visible "within a few minutes" [VGI-F06] of a sale. A tighter branch closer to one minute [VGI-F07] would change staffing, but that is not stated as the current requirement.
  • Scalability: sustain roughly 900,000 basket events per day [VGI-F05] with a weekday-evening peak [VGI-F05].
  • Integrity / recoverability: Zero basket-event loss [VGI-F16] (given), and any gap must be recoverable [VGI-F18].
  • Security / compliance: PCI DSS applies [VGI-F20], and cardholder data must never land in the analytics platform [VGI-F21].
  • Cost: cloud run-rate ceiling of USD 8,000 per month [VGI-F19] for the new platform.
  • Operability: workable for two full-time data engineers [VGI-F11] with no platform team [VGI-F12].

Decision 1 — Keep a sidecar near-real-time inventory path while retaining the finance warehouse

Chosen approach. Reuse the existing on-premises broker [VGI-F04] as the authoritative post-egress event feed, keep the overnight finance warehouse in service [VGI-F08], and add a sidecar near-real-time inventory projector rather than replacing finance's path in this phase.

Technology options (capability first, then ecosystem). The capability required is stateful event-driven inventory projection sourced from the existing broker while finance continues on the overnight warehouse path.
• Open-source / portable: Kafka Streams for broker-adjacent stateful projection, Apache Flink for keyed low-latency state, or Spark Structured Streaming if the team prefers a more SQL-centric projector. This is the default direction in Phase 2 because it reuses the existing broker [VGI-F04] and adds the least duplicate always-on cloud control plane under the USD 8,000/month [VGI-F19] ceiling.
• Platform / lakehouse: Databricks Structured Streaming + Workflows when the stock-serving layer already lives in a lakehouse, Snowflake Snowpipe Streaming + Tasks when the serving layer is warehouse-centric, or Confluent Cloud if the broker layer itself is what the team wants managed. These are secondary options here: they are only reasonable if a substantial part of the platform cost is already sunk elsewhere, because otherwise they add a new priced control plane on top of the retained broker and overnight warehouse.
• Hyperscaler-managed: Azure Event Hubs + Stream Analytics, Google Cloud Pub/Sub + Dataflow, or Amazon MSK/Kinesis + Glue are not the default recommendation in this phase for the same reason: they duplicate managed streaming and processing cost on top of the retained estate, so they must be proven to fit the USD 8,000/month [VGI-F19] ceiling before selection.
Selection driver: fastest safe path from the current broker to the stock-serving view, using the smallest additional priced footprint compatible with the budget ceiling [VGI-F19], not vendor familiarity.

Rejected alternative. Replace the overnight warehouse now with a single new end-to-end platform for both merchandising and finance.

Why the rejected alternative is genuinely viable. One platform would remove duplicate inventory logic, reduce reconciliation between operational and finance views, and avoid carrying both batch and near-real-time paths at once. If finance were free to move and the budget ceiling were much larger, consolidation could be the simpler long-term design.

What is sacrificed. This sidecar pattern keeps two inventory paths alive for a period, so reconciliation, semantic drift, and duplicate testing remain real engineering work.

What is gained. It directly protects the facts that the overnight warehouse is finance-critical [VGI-F08], cannot be switched off [VGI-F09], and monthly close must not regress [VGI-F10], while still improving operational freshness toward the "few minutes" target [VGI-F06] under the cloud cost ceiling [VGI-F19].

Reversal condition. Revisit this and collapse to one platform only after finance validates that the new path can replace the old warehouse without harming close activities, and only if the replacement still fits within the run-rate ceiling [VGI-F19].

Unresolved fact that could change this choice. The practical meaning of "not locked into one vendor" is still undefined [VGI-U04]. That unresolved fact can still change which managed or open-source implementation sits under this coexistence pattern, even though the coexistence pattern itself now stands.

Trade-off: temporary duplication and reconciliation burden, in exchange for reducing business and budget risk while inventory freshness improves.

Decision 2 — Lossless, replayable basket-event ledger and idempotent inventory projection

Chosen approach. Persist every compliant basket event in a durable replayable ledger, use acknowledgements and retention strong enough to preserve zero basket-event loss [VGI-F16] (given), and make the inventory projector idempotent so any gap can be replayed and recovered [VGI-F18].

Technology options. The capability required is a financially trustworthy event ledger whose gaps are recoverable, not merely observable.
• Open-source / portable: Kafka or Pulsar retention for replay, Kafka transactions or idempotent producers where appropriate, Flink checkpoints for reconstructable keyed state, and Iceberg or Delta Lake snapshots when the team wants portable recovery history. This is the default direction in Phase 2 because it extends the retained broker path [VGI-F04] rather than paying for a second premium managed ledger.
• Platform / lakehouse: Databricks checkpointed Structured Streaming when replay and serving stay together, Snowflake persistent history when warehouse-native recovery is preferred, or Confluent Cloud when durable broker retention is the main control point. These are conditional options only if an existing enterprise commitment or sunk platform spend makes them realistic inside the USD 8,000/month [VGI-F19] ceiling.
• Hyperscaler-managed: Azure Event Hubs Capture with durable downstream retention, Google Cloud Pub/Sub with a recoverable sink, or Amazon MSK/Kinesis with persisted downstream state are comparison targets, not the default recommendation, because they add managed-retention cost on top of the retained broker and still have to prove both zero basket-event loss [VGI-F16] (given) and budget fit [VGI-F19].
Selection driver: provable lossless replay and recovery at the lowest incremental run-rate compatible with the budget ceiling [VGI-F19], not a generic preference for "real time".

Rejected alternative. A best-effort projection that prioritizes freshness only, accepts local loss during faults, and relies on the overnight warehouse to self-heal inventory the next day.

Why the rejected alternative is genuinely viable. It is simpler for a small team, cheaper to operate, and often good enough for operational dashboards whose numbers can be corrected later. That was why Phase 1 could honestly leave this undecided before the finance and loss-tolerance facts were known.

What is sacrificed. Lossless replayability adds storage, stricter acknowledgement discipline, idempotency work in the projector, and more care around late or retried events.

What is gained. The design now satisfies the supplied facts that finance reconciles against this stream [VGI-F17], a missing basket is a missing sale on the books [VGI-F17], zero basket-event loss [VGI-F16] (given) is required, and any gap must be recoverable [VGI-F18].

Reversal condition. Revisit this decision only if the accounting source of record changes and finance no longer reconciles against this stream, because under the supplied facts the best-effort branch is no longer acceptable.

Unresolved fact that could change this choice. The unresolved vendor-lock-in boundary [VGI-U04] can still change whether lossless replay is delivered by an open broker stack or a managed platform feature, but it does not change the need for a lossless replayable ledger.

Trade-off: more state discipline, storage, and recovery engineering, in exchange for a finance-grade event stream where missing baskets are not tolerated and gaps remain recoverable. Phase 1's best-effort branch is now explicitly rejected as wrong for this fact pattern.

Decision 3 — Remove or tokenise cardholder data before the event leaves the store network

Chosen approach. Insert a store-egress sanitization/tokenization boundary so the event published downstream preserves the sale signal needed for inventory and finance, but cardholder data is removed or tokenised before the event leaves the store network [VGI-F21].

Technology options. The capability required is a CHD-before-egress sanitization boundary that satisfies the supplied PCI facts [VGI-F20] [VGI-F21] while preserving event utility downstream.
• Open-source / portable: a broker-side sanitizer or stream processor plus Vault-backed tokenization, or a lightweight edge service that emits a compliant event contract to Kafka, Pulsar, or another portable broker.
• Platform / lakehouse: Confluent stream processing plus external tokenization, or Databricks / Snowflake only after the compliant event contract has already been produced upstream.
• Hyperscaler-managed: Azure, Google Cloud, or AWS tokenization and secrets tooling may support this boundary, but the compliant event must exist before the analytics platform receives it [VGI-F21].
Selection driver: where the PCI boundary is enforced, not which analytics platform is most convenient.

Rejected alternative. Send the raw POS event to the cloud analytics platform and mask or tokenize it only after ingestion.

Why the rejected alternative is genuinely viable. It is operationally simpler, keeps fewer moving parts at the edge, and is a common pattern in lower-sensitivity pipelines because the full raw event is available to every downstream consumer from one place.

What is sacrificed. A new edge-processing boundary must be operated, observed, and tested; debugging can be harder because the downstream platform no longer sees raw cardholder fields.

What is gained. The design now satisfies the supplied facts that PCI DSS applies [VGI-F20] and cardholder data must never land in the analytics platform, but instead be removed or tokenised before events leave the store network [VGI-F21].

Reversal condition. Revisit the implementation details only if the downstream platform stops being an analytics platform for this stream or if the compliance boundary itself changes. Under the supplied PCI facts, post-ingestion masking is not an acceptable substitute.

Unresolved fact that could change this choice. The unresolved lock-in definition [VGI-U04] still affects whether tokenization and policy enforcement should be as vendor-neutral as possible or whether a managed provider's native controls are acceptable.

Trade-off: more edge-boundary engineering and a stricter data contract, in exchange for an architecture that satisfies the supplied PCI boundary facts [VGI-F20] [VGI-F21] by ensuring analytics never receives raw cardholder data. This replaces the Phase 1 position that governance/security was not yet architectural; that position was wrong once the PCI fact arrived.

9. Governance & Security Recommendations

Is governance/security an ASR here? Yes. The Phase 1 answer was wrong once the withheld facts arrived. PCI DSS applies [VGI-F20], and cardholder data must be removed or tokenised before the event leaves the store network [VGI-F21], so the compliance boundary shapes the ingestion topology itself. This report does not claim full PCI certification. It only reasons from the supplied facts about the egress boundary and analytics prohibition; broader PCI operating controls would need separate confirmation before anyone could claim end-to-end compliance status.

AreaRecommendation for this scenario
Data classificationClassify raw POS events that still contain cardholder elements as Restricted-PCI (derived from VGI-F20 and VGI-F21). Classify the post-egress sanitized event as Internal Operational (assumption) unless later facts raise it further.
Access-control modelUse a strict boundary between the Restricted-PCI zone and the analytics zone. Finance and merchandising should consume the compliant downstream contract, not raw cardholder data. Prefer tag-based policy if more consumer groups are added later.
PII / CHD protectionRemove or tokenise cardholder data before egress [VGI-F21]. Do not rely on masking after ingestion into analytics; that would violate the stated fact.
AuditabilityLog which edge transformation version produced each downstream event, which tokenization policy ran, and which replay operation reprocessed any recoverable gap [VGI-F18].
Lineage & data contractsTrack lineage from POS event [VGI-F03] through the PCI boundary [VGI-F21], into the lossless ledger [VGI-F16], then into the projector and overnight warehouse. Treat the compliant post-egress event schema as a governed contract.
Data quality & quarantineQuarantine malformed or non-compliant events rather than silently dropping them. Because zero basket-event loss is required [VGI-F16] (given), quarantine must preserve recoverability [VGI-F18], not discard evidence.
Secrets & keysKeep tokenization secrets and keys outside code, in a dedicated secrets manager. The exact product remains open to the still-undefined lock-in boundary [VGI-U04].

The most expensive decisions to reverse are now the compliant post-egress event contract [VGI-F21] and the lossless replay semantics required by finance [VGI-F16] [VGI-F18]. These are hard-right on the cost-of-change spectrum because downstream consumers, audit controls, and reconciliation procedures will all depend on them.

The cloud budget ceiling of USD 8,000 per month [VGI-F19] does more than make platform choice reversible: in this phase it can foreclose whole platform families whose managed control planes would duplicate the retained broker [VGI-F04] and overnight warehouse [VGI-F08]. Compute engines are still easier to swap than the PCI boundary or the zero-loss ledger semantics, but the budget means several managed-stack options may never be viable enough to select in the first place.
