Controlled Test

1. Business Context

Verdant Grocers operates 140 stores [VGI-F01] across three states [VGI-F02]. Today, store managers reorder from an overnight report, so a sell-out at 10 AM [VGI-F15] is not visible to replenishment until the next morning [VGI-F15].

The event path already exists: each store's point-of-sale terminals emit a transaction event per basket [VGI-F03], and those events reach an on-premises message broker today [VGI-F04]. The chain sees roughly 900,000 basket events per day [VGI-F05] with a pronounced weekday-evening peak [VGI-F05].

The corrected Phase 3 fact changes only the outage-loss assumption for the near-real-time inventory view. Each POS terminal keeps a local journal retained for 72 hours [VGI-F16], dropped streaming events are re-sent in the overnight batch [VGI-F17], and the business tolerates loss of up to roughly 15 minutes [VGI-F18] from the near-real-time view during an outage if the loss is visible to merchandising and corrected by the next morning [VGI-F18].

3. Functional & Quality Requirements

Functional Requirements

  • The system must consume basket-sale events from the existing flow.
  • The system must update store-level stock positions from those sales.
  • The system must expose an operational inventory view for merchandising and replenishment.
  • The system must continue feeding the overnight finance warehouse.
  • The system must make any near-real-time outage loss visible to merchandising [VGI-F18].
  • The system must rely on the POS journal plus overnight resend for financial recovery [VGI-F16] [VGI-F17].
  • The system must remove or tokenise cardholder data before events leave the store network [VGI-F21].

Quality Attributes

  • Freshness: stock positions visible "within a few minutes" [VGI-F06] of a sale. A tighter branch closer to one minute [VGI-F07] would change staffing, but that is not stated as the current requirement.
  • Scalability: sustain roughly 900,000 basket events per day [VGI-F05] with a weekday-evening peak [VGI-F05].
  • Outage behavior: the near-real-time view may lose up to roughly 15 minutes [VGI-F18] during an outage if that loss is visible to merchandising [VGI-F18] and corrected by the next morning [VGI-F18].
  • Recovery: POS journals are retained for 72 hours [VGI-F16], and dropped events are re-sent in the overnight batch [VGI-F17].
  • Security / compliance: PCI DSS applies [VGI-F20], and cardholder data must never land in the analytics platform [VGI-F21].
  • Cost: cloud run-rate ceiling of USD 8,000 per month [VGI-F19] for the new platform.
  • Operability: workable for two full-time data engineers [VGI-F11] with no platform team [VGI-F12].

Decision 1 — Keep a sidecar near-real-time inventory path while retaining the finance warehouse

Chosen approach. Reuse the existing on-premises broker [VGI-F04] as the authoritative post-egress event feed, keep the overnight finance warehouse in service [VGI-F08], and add a sidecar near-real-time inventory projector rather than replacing finance's path in this phase.

Technology options (capability first, then ecosystem). The capability required is stateful event-driven inventory projection sourced from the existing broker while finance continues on the overnight warehouse path.
• Open-source / portable: Kafka Streams for broker-adjacent stateful projection, Apache Flink for keyed low-latency state, or Spark Structured Streaming if the team prefers a more SQL-centric projector. This remains the default direction in Phase 3 because it reuses the existing broker [VGI-F04] and keeps the smallest additional priced footprint under the USD 8,000/month [VGI-F19] ceiling.
• Platform / lakehouse: Databricks Structured Streaming + Workflows when the stock-serving layer already lives in a lakehouse, Snowflake Snowpipe Streaming + Tasks when the serving layer is warehouse-centric, or Confluent Cloud if the broker layer itself is what the team wants managed. These remain secondary options because they add a priced control plane on top of the retained broker and overnight warehouse.
• Hyperscaler-managed: Azure Event Hubs + Stream Analytics, Google Cloud Pub/Sub + Dataflow, or Amazon MSK/Kinesis + Glue are still not the default recommendation in this phase because the budget ceiling [VGI-F19] disfavors duplicating the retained estate with a second fully managed control plane.
Selection driver: fastest safe path from the current broker to the stock-serving view, using the smallest additional priced footprint compatible with the budget ceiling [VGI-F19].

Rejected alternative. Replace the overnight warehouse now with a single new end-to-end platform for both merchandising and finance.

Why the rejected alternative is genuinely viable. One platform would remove duplicate inventory logic, reduce reconciliation between operational and finance views, and avoid carrying both batch and near-real-time paths at once. If finance were free to move and the budget ceiling were much larger, consolidation could be the simpler long-term design.

What is sacrificed. This sidecar pattern keeps two inventory paths alive for a period, so reconciliation, semantic drift, and duplicate testing remain real engineering work.

What is gained. It directly protects the facts that the overnight warehouse is finance-critical [VGI-F08], cannot be switched off [VGI-F09], and monthly close must not regress [VGI-F10], while still improving operational freshness toward the "few minutes" target [VGI-F06] under the cloud cost ceiling [VGI-F19].

Reversal condition. Revisit this and collapse to one platform only after finance validates that the new path can replace the old warehouse without harming close activities, and only if the replacement still fits within the run-rate ceiling [VGI-F19].

Unresolved fact that could change this choice. The practical meaning of "not locked into one vendor" is still undefined [VGI-U04]. That unresolved fact can still change which managed or open-source implementation sits under this coexistence pattern, even though the coexistence pattern itself now stands.

Trade-off: temporary duplication and reconciliation burden, in exchange for reducing business and budget risk while inventory freshness improves.

Decision 2 — Best-effort near-real-time projection with visible outage gaps and overnight correction

Chosen approach. Use a simpler best-effort near-real-time inventory projector that makes outage loss visible to merchandising [VGI-F18], tolerates loss of up to roughly 15 minutes [VGI-F18] in the near-real-time view during an outage, and relies on the POS journal retained for 72 hours [VGI-F16] plus overnight resend [VGI-F17] to correct the data by the next morning [VGI-F18].

Technology options. The capability required is a low-cost, operationally lightweight near-real-time projector whose outages are visible and whose financial recovery comes from the separate journal-and-batch path.
• Open-source / portable: Kafka Streams or Spark Structured Streaming with simple state stores and visible lag/health indicators, using the existing broker [VGI-F04] and the overnight resend path [VGI-F17]. This is now the default direction because it matches the corrected bounded-loss fact [VGI-F18] and keeps the run-rate lowest against the USD 8,000/month [VGI-F19] ceiling.
• Platform / lakehouse: Databricks, Snowflake, or Confluent-managed streaming remain viable only if the organization already absorbs part of their control-plane cost elsewhere; the corrected bounded-loss fact removes the strongest reason to pay for premium always-on durability in the real-time path.
• Hyperscaler-managed: Azure, Google Cloud, or AWS managed streaming can still work, but they are now even harder to justify as the default because the corrected fact no longer requires a lossless real-time ledger and therefore weakens the case for paying for stronger managed durability semantics.
Selection driver: lowest incremental run-rate and simplest operational footprint that still delivers the freshness goal [VGI-F06] and the bounded-loss outage behavior [VGI-F18].

Rejected alternative. Keep the Phase 2 lossless, replayable streaming ledger as the core of the near-real-time path.

Why the rejected alternative is genuinely viable. It gives stronger continuity during outages, reduces divergence between the real-time and overnight views, and avoids waiting until the next morning to correct missed events. That is why Phase 2 chose it under the then-stated fact pattern.

What is sacrificed. During an outage, merchandising may see an incomplete near-real-time view for up to roughly 15 minutes [VGI-F18], and the correction arrives by the next morning [VGI-F18] rather than through a lossless real-time replay path.

What is gained. The design now matches the corrected facts: POS journals retained for 72 hours [VGI-F16] provide the financial recovery mechanism, the overnight resend path [VGI-F17] satisfies reconciliation, and the business explicitly tolerates the bounded-loss near-real-time behavior [VGI-F18]. It also makes the USD 8,000/month [VGI-F19] ceiling easier to meet because the real-time path no longer needs the strongest durability semantics.

Reversal condition. Phase 1 pre-committed to simplify this decision if bounded loss proved acceptable and overnight correction proved operationally sufficient. That is now the stated fact pattern [VGI-F17] [VGI-F18]. Revisit this and move back toward a lossless real-time ledger only if the business later stops tolerating roughly 15 minutes [VGI-F18] of outage loss in the near-real-time inventory view, or if finance again needs to reconcile directly from the streaming path rather than from the journal-plus-overnight route.

Unresolved fact that could change this choice. The unresolved vendor-lock-in boundary [VGI-U04] can still change whether the bounded-loss projector is built from open components or a managed streaming service, but it does not restore the old reason for a lossless real-time ledger.

Trade-off: a bounded outage gap in the near-real-time inventory view, in exchange for lower cost and simpler operations because financial recovery now comes from the POS journal and overnight batch rather than from a lossless streaming ledger. This is the explicit Phase 3 change in the direction pre-committed in Phase 1.

Decision 3 — Remove or tokenise cardholder data before the event leaves the store network

Chosen approach. Insert a store-egress sanitization/tokenization boundary so the event published downstream preserves the sale signal needed for inventory and finance, but cardholder data is removed or tokenised before the event leaves the store network [VGI-F21].

Technology options. The capability required is a CHD-before-egress sanitization boundary that satisfies the supplied PCI facts [VGI-F20] [VGI-F21] while preserving event utility downstream.
• Open-source / portable: a broker-side sanitizer or stream processor plus Vault-backed tokenization, or a lightweight edge service that emits a compliant event contract to Kafka, Pulsar, or another portable broker.
• Platform / lakehouse: Confluent stream processing plus external tokenization, or Databricks / Snowflake only after the compliant event contract has already been produced upstream.
• Hyperscaler-managed: Azure, Google Cloud, or AWS tokenization and secrets tooling may support this boundary, but the compliant event must exist before the analytics platform receives it [VGI-F21].
Selection driver: where the PCI boundary is enforced, not which analytics platform is most convenient.

Rejected alternative. Send the raw POS event to the cloud analytics platform and mask or tokenize it only after ingestion.

Why the rejected alternative is genuinely viable. It is operationally simpler, keeps fewer moving parts at the edge, and is a common pattern in lower-sensitivity pipelines because the full raw event is available to every downstream consumer from one place.

What is sacrificed. A new edge-processing boundary must be operated, observed, and tested; debugging can be harder because the downstream platform no longer sees raw cardholder fields.

What is gained. The design still satisfies the supplied facts that PCI DSS applies [VGI-F20] and cardholder data must never land in the analytics platform, but instead be removed or tokenised before events leave the store network [VGI-F21].

Reversal condition. Revisit the implementation details only if the downstream platform stops being an analytics platform for this stream or if the compliance boundary itself changes. The corrected outage-loss fact does not alter this boundary.

Unresolved fact that could change this choice. The unresolved lock-in definition [VGI-U04] still affects whether tokenization and policy enforcement should be as vendor-neutral as possible or whether a managed provider's native controls are acceptable.

Trade-off: more edge-boundary engineering and a stricter data contract, in exchange for an architecture that satisfies the supplied PCI boundary facts [VGI-F20] [VGI-F21] by ensuring analytics never receives raw cardholder data. The Phase 3 loss-tolerance correction does not weaken this decision.

9. Governance & Security Recommendations

Is governance/security an ASR here? Yes. PCI DSS applies [VGI-F20], and cardholder data must be removed or tokenised before the event leaves the store network [VGI-F21], so the compliance boundary shapes the ingestion topology itself. This report does not claim full PCI certification. It reasons only from the supplied facts about the egress boundary and analytics prohibition; broader PCI operating controls would need separate confirmation before anyone could claim end-to-end compliance status.

AreaRecommendation for this scenario
Data classificationClassify raw POS events that still contain cardholder elements as Restricted-PCI (derived from VGI-F20 and VGI-F21). Classify the post-egress sanitized event as Internal Operational (assumption) unless later facts raise it further.
Access-control modelUse a strict boundary between the Restricted-PCI zone and the analytics zone. Finance and merchandising should consume the compliant downstream contract, not raw cardholder data. Prefer tag-based policy if more consumer groups are added later.
PII / CHD protectionRemove or tokenise cardholder data before egress [VGI-F21]. Do not rely on masking after ingestion into analytics; that would violate the stated fact.
AuditabilityLog which edge transformation version produced each downstream event, which tokenization policy ran, and when the near-real-time path signaled degraded freshness to merchandising [VGI-F18].
Lineage & data contractsTrack lineage from POS event [VGI-F03] through the PCI boundary [VGI-F21], into the best-effort projector, and into the overnight warehouse/journal resend path [VGI-F17]. Treat the compliant post-egress event schema as a governed contract.
Data quality & quarantineQuarantine malformed or non-compliant events rather than silently dropping them. Because correction relies on journal resend [VGI-F17], quarantine must preserve evidence and make the degradation visible, not silently discard it.
Secrets & keysKeep tokenization secrets and keys outside code, in a dedicated secrets manager. The exact product remains open to the still-undefined lock-in boundary [VGI-U04].
