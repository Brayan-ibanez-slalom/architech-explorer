1. Business Context

Verdant Grocers operates 140 stores [VGI-F01] across three states [VGI-F02]. Today, store managers reorder from an overnight report, so a sell-out at 10 AM [VGI-F15] is not visible to replenishment until the next morning [VGI-F15].

The current event path already exists: each store's point-of-sale terminals emit a transaction event per basket [VGI-F03], and those events already reach an on-premises message broker [VGI-F04]. The chain sees roughly 900,000 basket events per day [VGI-F05] with a pronounced weekday-evening peak [VGI-F05].

This report is intentionally conservative. The scenario withholds acceptable event loss during outage, any budget ceiling, and any compliance regime. Decisions that depend on those facts are marked PENDING VALIDATION rather than finalized.

3. Functional & Quality Requirements

Functional Requirements

  • The system must consume basket-sale events from the existing broker.
  • The system must translate sales into store-level stock-position updates.
  • The system must expose an operational inventory view for merchandising and replenishment.
  • The system must continue feeding the overnight finance warehouse.
  • The system must preserve a path to reconcile operational inventory outputs with finance outputs.

Quality Attributes

  • Freshness: stock positions visible "within a few minutes" [VGI-F06] of a sale. A tighter branch closer to one minute [VGI-F07] would change staffing, but that is not stated as the current requirement.
  • Scalability: sustain roughly 900,000 basket events per day [VGI-F05] with a weekday-evening peak [VGI-F05].
  • Operability: workable for two full-time data engineers [VGI-F11] with no platform team [VGI-F12].
  • Continuity: the overnight finance warehouse must remain in place [VGI-F08], cannot be switched off [VGI-F09], and monthly close must not regress [VGI-F10].
  • Durability / cost / compliance: acceptable event loss during outage was not stated [VGI-U01], any budget ceiling was not stated [VGI-U02], and any compliance regime was not stated [VGI-U03]. These are open questions, not hidden assumptions.

Decision 1 — Add a sidecar near-real-time inventory path while retaining the finance warehouse

Chosen approach. Introduce a separate near-real-time inventory projection fed from the existing on-premises broker [VGI-F04], while leaving the overnight finance warehouse untouched in Phase 1.

Technology options (capability first, then ecosystem). The capability required is stateful event-driven inventory projection sourced from an existing broker while a batch warehouse remains in service.
• Open-source / portable: Kafka Streams for in-log stateful projection, Apache Flink for low-latency keyed state, or Spark Structured Streaming if the team prefers a more SQL-centric path.
• Platform / lakehouse: Databricks Structured Streaming + Workflows when the stock view will already live in a lakehouse, Snowflake Snowpipe Streaming + Tasks when the serving layer is warehouse-centric, or Confluent Cloud when managed Kafka around the existing broker is the main goal.
• Hyperscaler-managed: Azure Event Hubs + Stream Analytics, Google Cloud Pub/Sub + Dataflow, or Amazon MSK/Kinesis + Glue only if Phase 2 later justifies moving the serving path into that cloud ecosystem.
Selection driver: the fastest path from the current broker to a stock-serving view, not vendor familiarity.

Rejected alternative. Replace the overnight warehouse now with a single new end-to-end platform for both merchandising and finance.

Why the rejected alternative is genuinely viable. One platform would remove duplicate inventory logic, reduce reconciliation between operational and finance views, and avoid carrying both batch and near-real-time paths at once. If finance were free to move, consolidation could be the simpler long-term design.

What is sacrificed. This sidecar pattern keeps two inventory paths alive for a period, so reconciliation, semantic drift, and duplicate testing become real engineering work.

What is gained. It directly protects the facts that the overnight warehouse is finance-critical [VGI-F08], cannot be switched off [VGI-F09], and monthly close must not regress [VGI-F10], while still improving operational freshness toward the "few minutes" target [VGI-F06].

Reversal condition. Revisit this and collapse to one platform only after finance validates that the new path can replace the old warehouse without harming close activities, because that is the only condition under which the coexistence constraint disappears.

Unresolved fact that could change this choice. A budget or cost ceiling was not stated [VGI-U02]. If Phase 2 reveals budget for a broader replacement program, the organization might rationally choose consolidation sooner instead of carrying coexistence overhead.

Trade-off: temporary duplication and reconciliation burden, in exchange for reducing business risk to the existing finance flow while inventory freshness improves.

Decision 2 — Replayable inventory state with durability semantics (PENDING VALIDATION)

Provisional direction. Preserve a replayable event history and build inventory projection updates to be idempotent, but do not finalize acknowledgement mode, replica policy, or outage-recovery semantics until acceptable event loss is stated.

Technology options. The capability required is reconstructable inventory state after faults, without silently inventing a durability target.
• Open-source / portable: Kafka or Pulsar retention for replay, Flink checkpoints for reconstructable keyed state, and Iceberg or Delta Lake snapshots when the team wants engine-portable recovery history.
• Platform / lakehouse: Databricks checkpointed Structured Streaming when replay and serving stay together, Snowflake persistent history when warehouse-native recovery is preferred, or Confluent Cloud when durable broker retention is the primary control point.
• Hyperscaler-managed: Azure Event Hubs Capture, Google Cloud Pub/Sub with a durable recovery sink, or Amazon MSK/Kinesis with persisted downstream state if managed durability becomes worth the cost.
Selection driver: the measured loss tolerance once the stakeholder supplies it, not a generic preference for "more durable".

Rejected alternative. A best-effort projection that prioritizes freshness only, accepts local loss during faults, and relies on the overnight warehouse to self-heal inventory the next day.

Why the rejected alternative is genuinely viable. It is simpler for a small team, cheaper to operate, and might be good enough if the business can tolerate some temporary stock inaccuracy during outages because finance already has an overnight reconciliation path.

What is sacrificed. Replayability adds storage, state-management discipline, and a stricter data contract between the broker, projector, and serving layer.

What is gained. If low-loss recovery is later required, replayable state gives a path to restore the stock view without forfeiting the current freshness goal of "a few minutes" [VGI-F06] under the chain load of roughly 900,000 basket events per day [VGI-F05].

Reversal condition. Revisit this and simplify to best-effort processing if Phase 2 shows bounded loss is acceptable and if overnight correction is operationally sufficient for merchandising.

Unresolved fact that could change this choice. Acceptable event loss during an outage was not stated [VGI-U01]. That missing fact is load-bearing: a stricter outage-loss target would push toward stronger replication and acknowledgment guarantees, while best-effort tolerance can justify a much lighter design.

Trade-off: more state discipline and storage now, in exchange for preserving a recovery path without pretending the scenario already gave an outage-loss target. This remains pending until Phase 2 answers VGI-U01.

Decision 3 — Preserve portability now; defer a deep single-vendor commitment (PENDING VALIDATION)

Provisional direction. Keep event contracts and persisted data in portable interfaces first, and narrow to a more integrated single-vendor stack only when budget, compliance, and lock-in boundaries are explicit.

Technology options. The capability required is optionality under a small-team operating model.
• Open-source / portable: Kafka or Pulsar for eventing, Flink or Spark for processing, Airflow or Dagster for orchestration, and Iceberg or Delta Lake for replayable storage when preserving exit options is the top priority.
• Platform / lakehouse: Databricks or Snowflake when the team decides lower day-1 operational burden outweighs tighter platform coupling, or Confluent-managed Kafka when the broker layer is the main service they want to outsource.
• Hyperscaler-managed: Azure-native, Google Cloud-native, or AWS-native streaming-and-storage stacks only when budget, compliance, and an explicit platform preference narrow the viable field.
Selection driver: the real meaning of "not locked into one vendor" [VGI-F13] once it is defined, balanced against the team-size constraint of two engineers [VGI-F11] and no platform team [VGI-F12].

Rejected alternative. Pick one integrated cloud or lakehouse stack immediately and optimize for lowest operational burden from day one.

Why the rejected alternative is genuinely viable. For a team this small, a single managed stack could materially reduce integration work, simplify monitoring, and shorten time to first value. If cost, compliance, and platform standardization all favored one ecosystem, it could be the most responsible choice.

What is sacrificed. A portability-first design can slow delivery by forcing extra integration seams and by forgoing some platform-native convenience features.

What is gained. It honors the explicit anti-lock-in statement [VGI-F13] while avoiding a fake precision about what that statement means in practice [VGI-F14]. It also keeps the most expensive-to-change assets — event contracts and persisted history — easier to move later.

Reversal condition. Revisit this and commit to a single managed stack if Phase 2 supplies a budget ceiling that rewards managed consolidation [VGI-U02], or a compliance regime that narrows the viable platforms [VGI-U03], or a concrete definition of acceptable lock-in [VGI-U04].

Unresolved fact that could change this choice. The scenario explicitly says anti-lock-in was not defined in practice [VGI-U04], and it also withholds any budget ceiling [VGI-U02] and any compliance regime [VGI-U03]. Until those are known, a deep platform commitment would be preference masquerading as architecture.

Trade-off: more integration discipline up front, in exchange for preserving optionality until the missing commercial and regulatory facts arrive. This is intentionally provisional.

9. Governance & Security Recommendations

Is governance/security an ASR here? Not yet on the current evidence. The scenario withholds any explicit compliance regime [VGI-U03], and it does not say whether basket events contain customer or payment identifiers. So governance/security is not elevated to a named ASR in Phase 1 — but it still requires design recommendations because the inventory view is shared data and the missing compliance answer could quickly make it architectural.

AreaRecommendation for this scenario
Data classificationClassify store/item/inventory telemetry as Internal Operational (assumption) by default. If basket events also carry customer or payment identifiers, raise the classification and re-evaluate controls once the compliance regime is stated [VGI-U03].
Access-control modelSeparate merchandising/replenishment access from finance access. A simple role model may be enough in Phase 1 (assumption), but prefer tag-based policy if more consumer groups or more sensitive fields are added later.
PII protectionIf customer-linked attributes are present, strip, tokenize, or hash them before they enter the operational stock view. Do not assume they are present; do not assume they are absent either.
AuditabilityLog who changed inventory projections, who overrode stock states, and which source event produced a visible stock movement. This is needed for operational trust even before a formal compliance regime is known.
Lineage & data contractsTrack lineage from POS sale event [VGI-F03] to inventory projection to batch warehouse feed, and define a contract for item/store/quantity semantics so the sidecar path and finance path do not drift silently.
Data quality & quarantineQuarantine impossible states (for example, duplicate event application or impossible negative balances) rather than silently dropping records or silently publishing bad stock data.
Encryption & secretsEncrypt in transit and at rest, and keep credentials in a secrets manager. The specific key-management bar depends on the compliance regime that was not stated [VGI-U03].
