Scenario Context

1. Business Context

A retail company operates 500 stores [RIOT-F01] equipped with IoT devices that continuously generate telemetry events. Operations teams want to use this data to monitor store and device conditions, detect operational issues, and support near-real-time analytics. The company expects the number of connected devices to grow as the platform expands to new regions.

What the System Must Do

  • Receive telemetry events from devices across all stores
  • Validate incoming events
  • Persist accepted events for downstream processing
  • Make data available to analytics and operational applications
  • Support new versions of device event schemas over time

Known Operating Conditions

  • 50K events/sec [RIOT-F02] peak ingestion bursts during business hours
  • p95 ingestion latency < 200ms [RIOT-F03] during peak load
  • Recovery from a single availability-zone failure in <30 sec [RIOT-F04]
  • Deploy a new event schema without pipeline downtime, <1 day [RIOT-F05]

Additional Context

  • Events may contain device, store, customer, or loyalty identifiers requiring controlled access
  • Device firmware evolves independently and may introduce new event schema versions
  • The delivery team has strong batch-processing experience but limited streaming experience

Decision 1 — Managed Streaming Ingestion (not batch)

Adopt a streaming ingestion platform with multi-AZ replication instead of a batch-only ingestion path.

Technology options (capability first, then ecosystem): the capability required is durable, ordered, replayable event ingestion sustaining 50K events/sec [RIOT-F02] at <200ms p95 [RIOT-F03].
• Open-source / portable: Apache Kafka, Apache Pulsar, or Redpanda, paired with Apache Flink for streaming processing.
• Platform / managed OSS: Confluent Cloud, Redpanda Cloud, or Databricks Structured Streaming with Auto Loader.
• Hyperscaler-managed: Azure Event Hubs, Google Cloud Pub/Sub, or Amazon MSK/Kinesis.
Selection driver: given the team's limited streaming experience (constraint C1), a managed offering in whichever ecosystem the client already operates reduces delivery risk more than any feature difference between these products.

Trade-off: Requires the team to build new streaming skills and operational practices vs. batch-only comfort — necessary because 50K events/sec [RIOT-F02] at <200ms p95 [RIOT-F03] cannot be met with batch processing alone. Managed services trade higher per-GB cost for lower operational burden, which is the right trade given C1.

Decision 2 — Schema Registry with Governed Evolution

Use a schema registry with backward/forward-compatible schema evolution (Avro/Protobuf), decoupled from consumer deployment cycles.

Technology options: the capability required is enforced compatibility checking so independently-evolving firmware cannot break live consumers.
• Open-source / portable: Confluent Schema Registry (community edition), Apicurio Registry, or Buf Schema Registry for Protobuf.
• Platform / lakehouse: Databricks Unity Catalog schema enforcement, or Delta Lake / Apache Iceberg schema evolution at the storage layer.
• Hyperscaler-managed: Azure Schema Registry (in Event Hubs), Google Cloud Managed Service for Apache Kafka, or AWS Glue Schema Registry.
Selection driver: choose whichever registry integrates natively with the streaming platform selected in Decision 1 — cross-ecosystem pairing adds avoidable operational friction.

Trade-off: Adds schema-governance overhead vs. the ability to roll out new firmware-driven event versions within a day without pipeline downtime. Using an open serialization format (Avro/Protobuf) keeps the contract portable even if the registry product changes.

Decision 3 — Multi-AZ Redundancy with Automated Failover

Design the ingestion and persistence tiers for multi-AZ redundancy with automated failover, rather than single-AZ deployment with manual recovery.

Technology options: the capability required is automated failover within 30 seconds [RIOT-F04]; the tolerable data loss during that failover is an open question.
• Open-source / portable: Kafka with min.insync.replicas and rack-aware replica placement across zones; Apache Iceberg or Delta Lake on zone-redundant object storage for the persistence tier.
• Platform: Databricks or Snowflake managed multi-AZ durability (failover handled by the platform).
• Hyperscaler-managed: zone-redundant configurations of Azure Event Hubs, Google Cloud Pub/Sub (regional by default), or Amazon MSK multi-AZ.
Selection driver: verify the measured failover time of the chosen option against the <30 sec [RIOT-F04] requirement — vendor "high availability" claims are not equivalent to a tested RTO.

Trade-off: Higher infrastructure cost (duplicated resources across AZs) vs. meeting the <30 sec [RIOT-F04] recovery requirement. This is a direct, quantifiable cost-for-availability exchange that should be confirmed against the (currently unstated) infrastructure budget.

Design Recommendations

10. Governance & Security Recommendations

The scenario states that events "may contain device, store, customer, or loyalty identifiers that require controlled access". Because the course lists security boundaries among the capabilities that are expensive to introduce later, these are treated as design concerns rather than later hardening.

Governance Recommendations

AreaRecommendation for this scenario
Data contracts & schema governanceDevice firmware evolves independently, so producer/consumer contracts with enforced backward/forward compatibility are mandatory — this is the mechanism that makes the <1 day [RIOT-F05], zero-downtime schema rollout achievable (Decision 2).
Catalog & lineageRegister telemetry datasets with owner, freshness, and sensitivity tags; capture lineage via the open OpenLineage standard so ops teams can trace an alert back to its originating device and schema version.
Data quality & quarantineValidation is an explicit functional requirement. Route rejected events to a dead-letter/quarantine topic rather than dropping them — silent loss would make ingestion-completeness unverifiable. Note: the course uses "zero event loss" as an illustrative measure [RIOT-X01]; it is not stated in this scenario’s operating conditions, so it is an open question [RIOT-U01], not a requirement.
Retention lifecycleDefine retention tiers for raw vs. aggregated telemetry. At 50K events/sec [RIOT-F02], retention policy is the dominant storage-cost driver.
Cost governance (FinOps)Tag resources by region/store cluster so cost per region is observable as the platform expands — otherwise regional growth hides cost regressions.

Security Recommendations

AreaRecommendation for this scenario
Data classificationClassify identifier fields at ingestion (device/store = Internal; customer/loyalty = Restricted-PII) and attach policies to tags rather than topic or table names, so new event schema versions inherit protection automatically.
Access control modelPrefer ABAC / tag-based column-level policy so ops teams can see device and store telemetry without exposing customer or loyalty identifiers — least privilege by default.
PII protectionTokenize or salted-hash customer/loyalty identifiers at the ingestion boundary where downstream analytics only need joinability, not the raw value. Encrypt in transit (TLS, including device-to-gateway) and at rest.
Device identity & trustAuthenticate devices individually (per-device certificates or keys) with rotation and revocation. Shared device credentials across 500 stores [RIOT-F01] create an unrevocable blast radius.
AuditabilityLog access to identifier-bearing fields separately from the data plane, tamper-evident, with retention aligned to the (currently unstated) compliance regime.
Network boundariesDefine clear trust boundaries between device ingress, processing, and serving zones; use private connectivity for the data plane where sensitivity demands it.

Anti-Patterns to Avoid

  • Shared device credentials across stores (no revocation granularity)
  • Masking applied only at the dashboard layer while raw telemetry stays exposed
  • Silent dropping of events that fail validation
  • Per-topic hand-rolled access rules that drift as new schema versions ship

Event schema & partitioning strategy (Decision 2)

The event schema and partitioning strategy is closest to near-irreversible — once hundreds of thousands of devices and downstream consumers depend on a partitioning key and schema contract, changing it requires coordinated migration across firmware, ingestion, and consumers. This justifies investing in schema governance (Decision 2) early, before scaling to more regions.

Do Not Invent Requirements

12. Open Questions for the Stakeholder

  • What is the required retention period for raw telemetry events?
  • What data loss is tolerable during an AZ failover? The scenario gives a <30 second [RIOT-F04] recovery target but no durability target — these are two different requirements, and assuming zero loss is an unsourced inference, not specified in the scenario (an assumption, not given) would materially change the replication design and its cost.
  • What is the specific access control policy (roles, masking rules) for device/store/customer/loyalty identifiers?
  • Is there a budget ceiling for infrastructure as the platform expands to new regions?
  • What is the target onboarding time for a new region/store cluster (analogous to a new-source SLA)?
  • Are there regulatory requirements (e.g., data residency per region) affecting where telemetry can be stored/processed?
  • Is there an existing cloud or data-platform commitment (AWS / Azure / Google Cloud / Databricks / Snowflake / on-prem)? Without this, tooling options in Section 8 are deliberately kept multi-ecosystem rather than assuming a vendor.
