Scenario Context

1. Business Context

A retail company operates 500 stores [RIOT-F01] equipped with IoT devices that continuously generate telemetry events. Operations teams want to use this data to monitor store and device conditions, detect operational issues, and support near-real-time analytics. The company expects the number of connected devices to grow as the platform expands to new regions.

What the System Must Do

  • Receive telemetry events from devices across all stores
  • Validate incoming events
  • Persist accepted events for downstream processing
  • Make data available to analytics and operational applications
  • Support new versions of device event schemas over time

Known Operating Conditions

  • 50K events/sec [RIOT-F02] peak ingestion bursts during business hours
  • p95 ingestion latency < 200ms [RIOT-F03] during peak load
  • Recovery from a single availability-zone failure in <30 sec [RIOT-F04]
  • Deploy a new event schema without pipeline downtime, <1 day [RIOT-F05]

Additional Context

  • Events may contain device, store, customer, or loyalty identifiers requiring controlled access
  • Device firmware evolves independently and may introduce new event schema versions
  • The delivery team has strong batch-processing experience but limited streaming experience

Decision 1 — Managed Streaming Ingestion (not batch)

Adopt a streaming ingestion platform with multi-AZ replication instead of a batch-only ingestion path.

Technology options (capability first, then ecosystem): the capability required is event ingestion sustaining 50K events/sec [RIOT-F02] at <200ms p95 [RIOT-F03]. Ordering scope, replay window and acknowledgement semantics are not specified in the scenario [RIOT-U06]; they are stated here as open questions, not as required properties. They are exactly the properties that would differentiate these platforms, so the choice between them cannot be finalised until the RPO is answered.
• Open-source / portable: Apache Kafka, Apache Pulsar, or Redpanda, paired with Apache Flink for streaming processing.
• Platform / managed OSS: Confluent Cloud, Redpanda Cloud, or Databricks Structured Streaming with Auto Loader.
• Hyperscaler-managed: Azure Event Hubs, Google Cloud Pub/Sub, or Amazon MSK/Kinesis.
Selection driver: given the team's limited streaming experience (constraint C1), a managed offering in whichever ecosystem the client already operates reduces delivery risk more than any feature difference between these products.

Rejected alternative. Micro-batch ingestion on a short interval — the team's existing batch toolchain, run every few seconds rather than hourly.

Why the rejected alternative is genuinely viable. It is not a straw man. The team has strong batch-processing experience [RIOT-F08], and micro-batch reuses tooling, skills and operational practice they already have. The reason it is rejected is specific and measurable, not stylistic: the requirement is a p95 [RIOT-F03] ingestion latency of <200ms [RIOT-F03]. A micro-batch trigger interval sets a latency floor roughly equal to the interval, so meeting a 200ms p95 [RIOT-F03] would require a sub-200ms [RIOT-F03] batch interval — at which point it is streaming with extra scheduling overhead.

What the chosen approach sacrifices. The team must build streaming skills and on-call practice it does not have [RIOT-F08], which is a delivery risk, not just a training cost. Managed offerings also cost more per GB and give up low-level control.

What the chosen approach gains. It is the only option that can meet <200ms p95 [RIOT-F03] at 50K events/sec [RIOT-F02] without the latency floor above, and a managed offering keeps the new operational burden as small as possible given the skills gap.

Reversal condition. Revisit if the p95 [RIOT-F03] latency requirement is relaxed — if the true need is "near real time" rather than a hard 200ms [RIOT-F03], micro-batch becomes the better choice on skills and cost alone. Also revisit if measured managed-service cost at 50K events/sec [RIOT-F02] exceeds the budget, which is unstated [RIOT-U03].

Trade-off: a real skills and delivery risk for a batch-experienced team [RIOT-F08], plus higher per-GB managed cost, in exchange for the only design that meets <200ms p95 [RIOT-F03] at 50K events/sec [RIOT-F02]. Note the boundary: this justifies streaming; it does not by itself justify any particular durability or replication guarantee — see Decision 3.

Decision 2 — Schema Registry with Governed Evolution

Use a schema registry with backward/forward-compatible schema evolution (Avro/Protobuf), decoupled from consumer deployment cycles.

Technology options: the capability required is enforced compatibility checking so independently-evolving firmware cannot break live consumers.
• Open-source / portable: Confluent Schema Registry (community edition), Apicurio Registry, or Buf Schema Registry for Protobuf.
• Platform / lakehouse: Databricks Unity Catalog schema enforcement, or Delta Lake / Apache Iceberg schema evolution at the storage layer.
• Hyperscaler-managed: Azure Schema Registry (in Event Hubs), Google Cloud Managed Service for Apache Kafka, or AWS Glue Schema Registry.
Selection driver: where compatibility is enforced, not which product is most convenient. An earlier revision said "choose whichever registry integrates natively with the streaming platform" — that is circular, and it also listed storage-layer schema evolution (Delta/Iceberg) as equivalent to a registry. It is not: storage-layer evolution protects the table, it does not stop an incompatible producer from breaking live streaming consumers. Enforcement must sit at the producer boundary.

Rejected alternative. Consumer-side tolerant reading: no registry, no producer-side gate; each consumer defensively ignores unknown fields and defaults missing ones.

Why the rejected alternative is genuinely viable. It is the lowest-friction option, adds no infrastructure, and is a well-established pattern. With few consumers it works, and it never blocks a firmware rollout — which matters because firmware evolves independently [RIOT-F07] and is not centrally controlled.

What the chosen approach sacrifices. A central gate that can block a firmware release. If a device fleet ships a breaking schema, the registry rejects it — good for consumers, but the fleet may already be deployed in 500 stores [RIOT-F01] and not easily recalled. This decision accepts a coordination cost between firmware and platform teams that the tolerant-reader approach avoids entirely.

What the chosen approach gains. Compatibility is checked once, centrally, rather than depending on every consumer being written defensively — which is what makes "deploy a new event schema without pipeline downtime" [RIOT-F05] a property of the system rather than a hope about each consumer's code quality.

Reversal condition. Revisit if firmware release cycles cannot absorb a compatibility gate, or if the registry becomes an availability dependency on the ingest path. In either case, move enforcement to a validating consumer at the boundary and keep tolerant readers behind it.

Unresolved fact. Whether the firmware team can accept a blocking compatibility check before release is not stated [RIOT-U07]. This decision is not safe to finalise without that answer.

Trade-off: schema-governance overhead and a coordination dependency on the firmware team, in exchange for making no-downtime schema deployment [RIOT-F05] a structural guarantee rather than a per-consumer convention. An open serialisation format (Avro/Protobuf) keeps the contract portable if the registry product changes.

Decision 3 — Automated cross-AZ failover now; defer persistence semantics until the RPO is known

Chosen approach. Design the ingestion and persistence tiers for automated cross-AZ failover, and verify by workload-level test that recovery completes within <30 sec [RIOT-F04]. Do not yet fix acknowledgement mode, replica counts, or a lossless persistence guarantee: the scenario states a recovery time but no tolerable data loss [RIOT-U01].

Rejected alternative. Self-managed Kafka spread across AZs with min.insync.replicas, rack-aware placement and operator-controlled failover.

Why the rejected alternative is genuinely viable. It can meet the same 30-second target and gives explicit control over placement, acknowledgement policy, portability and failure testing. It is a credible architecture, not a straw man — and it is the stronger choice if the RPO turns out to be zero.

What the chosen approach sacrifices. Lower-level control, some portability, and probably lower unit cost at sustained scale. Its real failover and durability behaviour depends on vendor implementation and must be measured, because a "highly available" label is not a tested RTO.

What the chosen approach gains. Materially lower operational burden, which matters here because the scenario states the team has strong batch experience but limited streaming experience [RIOT-F08]. It reaches a testable 30-second recovery sooner and with less operational risk.

Reversal condition. Revisit this decision if (a) measured failover misses <30 sec [RIOT-F04], (b) the answer to the RPO requires acknowledgement or replication guarantees the managed service cannot demonstrate, or (c) measured cost exceeds the stakeholder-approved budget. Under any of these, move to the self-managed cross-AZ design.

Unresolved fact that could change this choice. The tolerable event loss (RPO) [RIOT-U01]. The three possible answers lead to different architectures, and this is the point at which they diverge:

Technology options:
• Open-source / portable: Kafka with min.insync.replicas and rack-aware placement; Apache Iceberg or Delta Lake on zone-redundant object storage.
• Platform: Databricks or Snowflake managed multi-AZ (failover handled by the platform).
• Hyperscaler-managed: zone-redundant Azure Event Hubs, Google Cloud Pub/Sub (regional by default), or Amazon MSK multi-AZ.
Selection driver: measured failover time, not vendor availability labels.

Trade-off: duplicated cross-AZ resources and reduced low-level control, in exchange for a testable <30 sec [RIOT-F04] recovery reached with an operationally realistic path for a team with limited streaming experience [RIOT-F08]. Note what this trade-off deliberately does not settle: the durability semantics above remain open, because the scenario never gave an RPO. An earlier revision of this report selected "durable, ordered, replayable" ingestion anyway — that was reasoning from an assumption, not from the scenario.

10. Governance & Security Recommendations

The scenario states that events "may contain device, store, customer, or loyalty identifiers that require controlled access". Because the course lists security boundaries among the capabilities that are expensive to introduce later, these are treated as design concerns rather than later hardening.

Governance Recommendations

AreaRecommendation for this scenario
Data contracts & schema governanceDevice firmware evolves independently, so producer/consumer contracts with enforced backward/forward compatibility are mandatory — this is the mechanism that makes the <1 day [RIOT-F05], zero-downtime schema rollout achievable (Decision 2).
Catalog & lineageRegister telemetry datasets with owner, freshness, and sensitivity tags; capture lineage via the open OpenLineage standard so ops teams can trace an alert back to its originating device and schema version.
Data quality & quarantineValidation is an explicit functional requirement. Route rejected events to a dead-letter/quarantine topic rather than dropping them — silent loss would make ingestion-completeness unverifiable. Note: the course uses "zero event loss" as an illustrative measure [RIOT-X01]; it is not stated in this scenario’s operating conditions, so it is an open question [RIOT-U01], not a requirement.
Retention lifecycleDefine retention tiers for raw vs. aggregated telemetry. At 50K events/sec [RIOT-F02], retention policy is the dominant storage-cost driver.
Cost governance (FinOps)Tag resources by region/store cluster so cost per region is observable as the platform expands — otherwise regional growth hides cost regressions.

Security Recommendations

AreaRecommendation for this scenario
Data classificationClassify identifier fields at ingestion (device/store = Internal; customer/loyalty = Restricted-PII) and attach policies to tags rather than topic or table names, so new event schema versions inherit protection automatically.
Access control modelPrefer ABAC / tag-based column-level policy so ops teams can see device and store telemetry without exposing customer or loyalty identifiers — least privilege by default.
PII protectionTokenize or salted-hash customer/loyalty identifiers at the ingestion boundary where downstream analytics only need joinability, not the raw value. Encrypt in transit (TLS, including device-to-gateway) and at rest.
Device identity & trustAuthenticate devices individually (per-device certificates or keys) with rotation and revocation. Shared device credentials across 500 stores [RIOT-F01] create an unrevocable blast radius.
AuditabilityLog access to identifier-bearing fields separately from the data plane, tamper-evident, with retention aligned to the (currently unstated) compliance regime.
Network boundariesDefine clear trust boundaries between device ingress, processing, and serving zones; use private connectivity for the data plane where sensitivity demands it.

Anti-Patterns to Avoid

  • Shared device credentials across stores (no revocation granularity)
  • Masking applied only at the dashboard layer while raw telemetry stays exposed
  • Silent dropping of events that fail validation
  • Per-topic hand-rolled access rules that drift as new schema versions ship

The event schema and partitioning strategy is closest to near-irreversible — once hundreds of thousands of devices and downstream consumers depend on a partitioning key and schema contract, changing it requires coordinated migration across firmware, ingestion, and consumers. This justifies investing in schema governance (Decision 2) early, before scaling to more regions.

Do Not Invent Requirements

12. Open Questions for the Stakeholder

  • What is the required retention period for raw telemetry events?
  • What data loss is tolerable during an AZ failover? The scenario gives a <30 second [RIOT-F04] recovery target but no durability target — these are two different requirements, and assuming zero loss is an unsourced inference, not specified in the scenario (an assumption, not given) would materially change the replication design and its cost.
  • What is the specific access control policy (roles, masking rules) for device/store/customer/loyalty identifiers?
  • Is there a budget ceiling for infrastructure as the platform expands to new regions?
  • What is the target onboarding time for a new region/store cluster (analogous to a new-source SLA)?
  • Are there regulatory requirements (e.g., data residency per region) affecting where telemetry can be stored/processed?
  • Is there an existing cloud or data-platform commitment (AWS / Azure / Google Cloud / Databricks / Snowflake / on-prem)? Without this, tooling options in Section 8 are deliberately kept multi-ecosystem rather than assuming a vendor.
