Module Recap

1. What the Course Teaches

Architecture is justified decision-making under constraint — not a choice of trendy tools. The module builds from understanding → application → judgment.

Understand

Architecture = decisions & trade-offs. Functional vs. quality attributes. ASRs and cost of change.

Apply

Identify objectives/constraints. Write measurable QA scenarios. Build a Utility Tree.

Evaluate

Judge if a decision is justified. Spot hidden trade-offs. Facilitate the objectives → decisions chain.

Key Takeaways

  • Start with the problem space, not the solution.
  • Quality attributes only matter when they are specific and measurable.
  • Not every requirement is architecturally significant — ASRs narrow the design space.
  • The harder a decision is to reverse, the more deliberate it must be.
  • Architecture must evolve: design upfront for critical capabilities, allow details to evolve, preserve optionality, reassess continuously.

Why Each ASR Is Architecturally Significant (explicit justification)

ASRJustification
ASR 1 — Identity Resolution at ScaleEvery downstream objective (trusted view, analytics, DS models) depends on correctly matching 20M+ customers across 4+ systems; getting this wrong doesn't degrade one feature — it invalidates the platform's core value proposition, and the matching logic is expensive to change once sources depend on it (near-irreversible per Cost of Change, Section 12).
ASR 2 — Tiered Freshness RequirementsThe same platform must satisfy three different latency SLAs (hours / 15 min / 7 AM) simultaneously — this cannot be solved by picking one ingestion pattern, it forces a structural (layered) decision that touches every source and consumer, which is the definition of an ASR (per ATAM: quality attributes that force competing design responses).
ASR 3 — Auditable PII Access Under ExtensibilitySecurity/audit requirements must hold even as 2–4 new sources are added per year within a 2-week SLA — if access control is bolted on per-source instead of centralized, every future onboarding cycle re-opens compliance risk, so this requirement shapes the connector architecture itself, not just a feature within it.

9. Architecture Decisions & Trade-offs

The "¿Para qué?" test applied to each decision below. Before naming any tool, each decision must answer: What outcome does this serve? Which business objective does it trace back to? Which quality attribute or ASR makes it necessary rather than optional? A recommendation that cannot answer all three is a preference, not a justified decision.

Decision 1 — Hybrid Ingestion Architecture

Use micro-batch/streaming for Customer Service-facing events (≤15 min SLA) and standard batch for marketing/dashboard data (7 AM SLA).

Technology options (capability first, then ecosystem): the capability required is a streaming/micro-batch ingestion path sustaining the ≤15 min SLA alongside a batch path for the 7 AM SLA.
• Open-source / portable: Apache Kafka or Apache Pulsar + Apache Flink (streaming-native) or Spark Structured Streaming; Airflow or Dagster for batch orchestration.
• Platform / lakehouse: Databricks (Auto Loader + Structured Streaming + Workflows), Snowflake (Snowpipe Streaming + Dynamic Tables + Tasks), Confluent Cloud.
• Hyperscaler-managed: Azure Event Hubs + Data Factory, Google Cloud Pub/Sub + Dataflow, or Amazon MSK/Kinesis + Glue.
Selection driver: pick by team skills and existing platform commitment — not by vendor. With no stated cloud commitment, a portable Kafka/Flink or lakehouse-native option preserves optionality.

Trade-off: Higher operational complexity (two pipelines) vs. cheaply meeting divergent latency SLAs — avoids over-engineering everything to real-time. (Consistent with the "Performance Efficiency" pillar across AWS/Azure/GCP Well-Architected frameworks: match the solution to the actual requirement, not the tightest one.)

Decision 2 — Dedicated Identity Resolution Service

Build a decoupled golden-record / identity-resolution layer with survivorship rules, separate from source ingestion.

Technology options: the capability required is explainable, auditable match/merge across 20M+ customers and 4+ systems, with the ability to reprocess history when rules change.
• Open-source / portable: Zingg (ML-based entity resolution) or Splink (probabilistic record linkage) running on Spark.
• Platform / lakehouse: Databricks (Spark ML matching pipelines + Delta time travel for reprocessing), Snowflake (Snowpark-based matching).
• Commercial specialist: Senzing, Informatica MDM, Reltio, Tamr.
• Hyperscaler-managed: AWS Entity Resolution (note: narrower portability).
Selection driver: explainability and auditability of merges matter most here because PII is involved — favor options whose match decisions can be inspected and replayed.

Trade-off: Upfront investment in matching logic vs. long-term trust and reduced rework; near-irreversible once adopted, so worth designing early. Recommend capturing this decision as an ADR (Architecture Decision Record) given its low reversibility, and choosing an open table format (Iceberg/Delta) for the golden-record store to avoid locking the most expensive-to-change asset into one engine.

Decision 3 — Standard Connector Framework with Centralized Access Control

Schema-on-write connector standard plus centralized, attribute-level access control & audit logging (not bolted on per source).

Technology options: the capability required is a repeatable source-onboarding path meeting the ≤2-week SLA, with PII policy enforced centrally rather than per source.
• Open-source / portable: Airbyte (OSS) or Meltano for connectors; Open Policy Agent (OPA) or Apache Ranger for centralized policy; OpenMetadata or DataHub for catalog/lineage.
• Platform / lakehouse: Databricks Unity Catalog (tag-based ABAC, row filters, column masks) or Snowflake Horizon (dynamic masking, row access policies, tag-based policies).
• Commercial: Fivetran/Matillion for connectors; Immuta or Privacera for policy enforcement; Collibra/Alation/Atlan for governance.
• Hyperscaler-native: Microsoft Purview + ADF, Google Dataplex + Data Fusion, or AWS Lake Formation + Glue.
Selection driver: prefer tag/attribute-based policy that scales as 2–4 new sources arrive per year; per-table grant models tend to drift into audit gaps.

Trade-off: More upfront design cost vs. hitting the ≤2-week onboarding SLA and consistent PII governance as sources scale. Centralized policy engines (OPA) maximize portability across engines; platform-native enforcement (Unity Catalog / Horizon) is simpler but must be re-implemented if the platform changes.

Design Recommendations

11. Governance & Security Recommendations

The course lists security boundaries and data isolation among the capabilities that are expensive to introduce later. Because this scenario explicitly involves PII and continuously growing sources, governance and security are treated here as design concerns, not post-build add-ons.

Is Governance/Security an ASR Here?

Yes — ASR 3 already captures it. "Auditable PII access under extensibility" qualifies because the requirement shapes the connector architecture itself: if access control is implemented per source rather than centrally, every 2-week onboarding cycle re-opens compliance risk. That is a structural consequence, which is the test for architectural significance.

Governance Recommendations

AreaRecommendation for this scenario
Ownership & stewardshipAssign a data owner per source domain (e-commerce, loyalty, support, marketing). Unowned sources become untrusted — which directly undermines objective O1 ("trusted view").
Catalog & discoverabilityRegister every dataset with business definitions, owner, freshness, and sensitivity tags. Without this, the "trusted customer view" fails at adoption even if the pipeline is technically correct.
Lineage & traceabilityCapture column-level lineage source → transformation → consumption; prefer the open OpenLineage standard to preserve engine optionality. Required to answer "where did this number come from?" for leadership's daily metrics.
Data contracts & schema governanceDefine explicit producer/consumer contracts with backward-compatible evolution, so the 4 source systems can change independently without breaking the 7 AM dashboard SLA.
Data qualityExpress expectations as measurable checks (completeness, uniqueness of customer keys, freshness). Decide explicitly whether a failed check blocks or alerts — a real trade-off between trust and availability against the 7 AM deadline.
Quarantine pathRoute rejected/unresolvable records to a dead-letter store rather than dropping them silently — essential when identity resolution cannot confidently match a customer.
Master data rulesMake survivorship rules (which source wins per attribute) explainable and auditable, and retain the ability to reprocess history when rules change — otherwise the matching logic becomes permanently frozen.
Cost governance (FinOps)Tag resources by domain and make cost per pipeline/consumer observable — directly satisfies constraint C2 ("costs must remain observable as usage grows").

Security Recommendations

AreaRecommendation for this scenario
Data classificationClassify at ingestion (Public / Internal / Confidential / Restricted-PII) and propagate classification as metadata through every layer. Attach policies to tags, not table names — this is what lets security scale as 2–4 new sources arrive per year.
Access control modelPrefer ABAC / tag-based policy over per-table RBAC grants. With continuous source growth, RBAC grant sprawl is the predictable failure mode. Enforce least privilege and purpose-based access.
PII protectionApply dynamic masking for Customer Service views that need the row but not the raw value; tokenization where referential integrity across systems is required without exposing values; salted hashing for join keys; encryption at rest and in transit as a non-negotiable baseline.
AuditabilityLog who accessed what, when, and for what purpose. Store audit logs separately from the data plane and make them tamper-evident — the scenario's "auditable access" wording makes this a hard requirement, not a nice-to-have.
Environment isolationNever use raw production PII in development or test. Mask or synthesize — a common and avoidable breach vector during a 4-month delivery crunch (constraint C1).
Secrets & keysNo secrets in pipeline configs or code; use a secrets manager (HashiCorp Vault, Key Vault, Secret Manager, or equivalent). Decide explicitly whether customer-managed keys (CMK/BYOK) are required — this is a regulatory question, not a preference.
Data Science / ML pathsApply the same classification and masking policies to feature stores and training sets as to BI consumption. Models can memorize and leak PII — the scenario explicitly anticipates churn/propensity models.

Anti-Patterns to Avoid in This Design

  • Per-source, hand-rolled access rules (guarantees drift and audit gaps as sources grow)
  • Security added after the pipeline works ("we'll lock it down later") — especially tempting under the 4-month deadline
  • Masking applied only at the dashboard layer while the underlying store stays exposed
  • Catalog and lineage treated as documentation rather than as enforced controls
  • Silent dropping of records that fail identity resolution

12. Cost of Change — Where Do These Decisions Sit?

The harder a decision is to reverse, the more intentional we should be about making it.

Reversible Partially Reversible Near-Irreversible
Dashboard layout, report formats
Choice of streaming tool for speed layer
Connector framework standard (Decision 3)
Classification scheme & access-control model
Identity resolution model / golden record schema & table format (Decision 2)

Decision 2 (Identity Resolution) sits closest to near-irreversible — once source systems and downstream consumers depend on a given golden-record model, changing the matching/survivorship logic requires reprocessing history and re-validating trust. This justifies investing in it early and getting it right before scaling to more sources.

Governance is also near-irreversible. The data classification scheme and access-control model are plotted deliberately far right: once dozens of datasets and consumers depend on a given tagging and policy structure, retrofitting a different model means re-classifying every asset and re-validating every grant. This is why governance belongs in the upfront design, not in a later hardening phase.

Lock-in note (preserve optionality). Storage format is the most expensive thing to change here, so favour an open table format (Apache Iceberg or Delta Lake) for the golden-record store. Compute engines, orchestrators, and connectors are comparatively replaceable; a proprietary storage format freezes the one decision you least want frozen. Where a platform-native policy engine is chosen (Unity Catalog, Snowflake Horizon), accept that policy definitions are a re-implementation cost if the platform changes — a legitimate trade-off, but one to make knowingly.

Do Not Invent Requirements

13. Open Questions for the Stakeholder

  • What is the required data retention policy beyond the existing 3 years of history?
  • Is there a specific compliance regime (GDPR, CCPA, etc.) governing PII beyond "controlled and auditable"?
  • What is the acceptable identity-match accuracy / false-merge tolerance for customer resolution?
  • Is there a target/cap on infrastructure cost (e.g., $/customer/month), or is "observability" the only requirement?
  • Do Data Science workloads have their own latency/freshness SLA, or is daily batch acceptable?
  • Is there an existing cloud or data-platform commitment (AWS / Azure / Google Cloud / Databricks / Snowflake / on-prem)? This is the single biggest factor in narrowing the tooling options in Section 9 — without it, we deliberately keep multi-ecosystem options open rather than assuming a vendor.
  • Are there data residency or sovereignty requirements constraining where customer data may be stored or processed?
  • Is right-to-erasure (customer data deletion) required? This must be answered before finalizing an append-only/immutable storage design, since it materially changes the storage architecture.
  • Are customer-managed encryption keys (CMK/BYOK) required, or is provider-managed encryption acceptable?
  • Should failed data-quality checks block the pipeline or alert only? This trades trust against hitting the 7:00 AM dashboard deadline.
  • What attainment percentile and measurement window apply to the 15-minute Customer Service SLA (e.g. p95 over a rolling day)? Only the bound was given, not the reliability target.
  • What is the precise latency tolerance for Marketing data? "Several hours" was given, which is not yet a measurable bound.
  • What level of disruption to existing pipelines is acceptable while onboarding a new source? The 2-week SLA was given; the permitted impact was not.
  • Is there a budget ceiling or unit-cost target (e.g. $/customer/month)? "Costs must remain observable" specifies visibility, not a threshold.
