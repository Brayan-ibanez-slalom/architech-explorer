GitHub Issue #12

1. Business Context

Solstice Health is a regional nonprofit health network with 12 primary-care clinics [SOLH-F01]. Referrals from primary-care physicians to specialists are currently tracked in a shared Excel sheet — no data warehouse or integration layer exists today, and the Excel sheet is the only current system of record for referrals [SOLH-F16] — which causes lost referrals and delayed specialist visits.

All 12 clinics [SOLH-F17] already emit HL7 v2 ADT feeds [SOLH-F17] from their EHR systems, and no clinic is willing to change EHR vendors for this project [SOLH-F18]. Any integration design must therefore ingest the existing HL7 v2 ADT feed format as-is, not a future or idealized format.

3. Functional & Quality Requirements

Functional Requirements

  • The system must ingest referral-relevant patient data from each clinic's EHR system via the existing HL7 v2 ADT feeds [SOLH-F17].
  • The system must match/de-duplicate patient identities across clinics before creating a referral record.
  • The system must route each referral to the correct specialist's work queue.
  • The system must notify the assigned care coordinator when a new referral arrives.
  • The system must provide role-based views so that the referring clinician, receiving specialist, and care coordinator each see only what their role permits [SOLH-F15].

Quality Attributes (how well)

  • Latency: a referral must reach the correct specialist's queue within 30 minutes of submission [SOLH-F04].
  • Availability: the system must be available 99.5% of the time [SOLH-F05] during business hours, defined as 7am-7pm local, Monday-Saturday [SOLH-F06].
  • Scalability: sustain a combined volume of roughly 4,000 referrals per week [SOLH-F03] across 12 clinics [SOLH-F01], with referral volume projected to grow 20% [SOLH-F07] year-over-year for the next 3 years [SOLH-F07].
  • Retention: referral and access-log data must be retained for 7 years [SOLH-F08], and every read/write access to a referral record must be logged and retained for the same 7 years [SOLH-F14].
  • Security: HIPAA applies because referral records contain PHI [SOLH-F13]; access must be restricted by role (referring clinician / specialist / care coordinator) [SOLH-F15].
  • Auditability: every read/write access to a referral record must be logged [SOLH-F14], satisfying the "complete, auditable access trail" objective (O3).

Decision 1 — Interface-Engine + Message-Queue Ingestion for the HL7 v2 ADT Feeds

Chosen approach. Adopt a healthcare interface engine that terminates each clinic's HL7 v2 ADT feed [SOLH-F17], converts it, and publishes it onto a durable message queue that the referral-routing service consumes as a light micro-batch/near-real-time path, rather than building a full low-latency streaming platform.

Rejected alternative. A true streaming platform (for example Apache Kafka or Azure Event Hubs with a stream-processing layer such as Apache Flink or Azure Stream Analytics) consuming the ADT feed with sub-second to few-second processing latency (illustrative measure only; is not a requirement stated in the issue).

Why the rejected alternative is genuinely viable. A real streaming platform gives the most latency headroom against the 30-minute bound [SOLH-F04] and the largest safety margin as volume grows 20% year-over-year for 3 years [SOLH-F07]; it is the textbook answer for a time-bounded routing requirement, and many healthcare integration platforms are built this way at larger scale.

What the chosen approach sacrifices. Some latency headroom and elasticity compared to a true streaming platform, and a design that would need real architectural rework — not just retuning — if the routing bound tightened well below today's 30-minute bound [SOLH-F04].

What the chosen approach gains. A pipeline the 4-person team can actually build and operate inside a 6-month timeline [SOLH-F09] and a $250,000 first-year budget [SOLH-F11], given the team is strong in SQL/Python but has no prior streaming-systems experience [SOLH-F10] — this is what makes the 30-minute [SOLH-F04] routing SLA achievable on schedule rather than merely theoretically possible.

Reversal condition. Revisit this and move to a true streaming platform if the routing bound is tightened well below the 30-minute bound [SOLH-F04], if measured queueing latency repeatedly threatens the 30-minute [SOLH-F04] bound at growth-adjusted volume, or if the team gains streaming operational experience.

Unresolved fact that could change this choice. No attainment percentile was given for the 30-minute bound [SOLH-U04], and the acceptable latency for the separate care-coordinator notification step was not stated [SOLH-U02]. If either turns out to be materially tighter than the routing bound itself, the queue-based design may not have enough margin.

Technology options (capability first, then ecosystem). The capability required is an HL7 v2 ADT-compatible interface engine feeding a durable queue, deployable inside the contracted Azure region [SOLH-F12].
• Open-source / portable: NextGen Connect (Mirth Connect) as the HL7 interface engine, publishing onto Apache Kafka or RabbitMQ running on Azure VMs/AKS — portable if the platform ever needs to move within Azure or to another region under a future BAA.
• Azure-native (required ecosystem per constraint [SOLH-F12]): Azure Health Data Services (FHIR/HL7 conversion) feeding Azure Service Bus or Azure Event Hubs, processed by Azure Functions or a small Python/SQL-based consumer service.
• Platform/lakehouse-native: Azure Databricks Structured Streaming (micro-batch mode) reading from Event Hubs, if the team later wants a single engine for both ingestion and downstream analytics.
Selection driver: the Azure BAA and residency requirement [SOLH-F12] mean every option must run inside the contracted region; within that constraint, prefer the interface-engine + queue pattern that matches the team's SQL/Python skillset [SOLH-F10] over a bespoke streaming build.

Trade-off: less latency headroom and a harder future migration to true streaming, in exchange for a design the team can deliver within the 6-month timeline [SOLH-F09] and the $250,000 first-year budget [SOLH-F11] without first learning to operate a streaming platform [SOLH-F10].

Decision 2 — Deterministic Patient-Identity Matching With a Manual Review Queue

Chosen approach. Match/de-duplicate patient identities across clinics using deterministic rules over existing HL7 identifiers (e.g. name, date of birth, and available medical-record/identifier segments), routing low-confidence matches to a manual review queue for a care coordinator, rather than building a probabilistic/ML matching service.

Rejected alternative. A probabilistic or ML-based entity-resolution service (in the style of Splink or Zingg) trained to score candidate matches across the 12 clinics' patient records.

Why the rejected alternative is genuinely viable. Probabilistic matching typically achieves higher recall on messy, inconsistently formatted real-world identifiers than fixed deterministic rules, and it scales more gracefully if Solstice Health onboards additional clinics beyond the current 12 [SOLH-F01] in the future. It is a legitimate long-term technical answer to identity resolution.

What the chosen approach sacrifices. Lower automatic match recall on inconsistently formatted identifiers, meaning more referrals fall into the manual review queue than a probabilistic system would produce, which adds care-coordinator workload.

What the chosen approach gains. Match decisions that are simple to explain and audit to a compliance reviewer, buildable by a SQL/Python-strong team with no prior streaming or ML-matching experience [SOLH-F10] inside the 6-month [SOLH-F09] timeline — directly supporting the auditable access trail objective (O3) [SOLH-F14] because every match decision traces to a specific, inspectable rule.

Reversal condition. Revisit this and move to probabilistic matching if the manual review queue's volume becomes operationally unsustainable at the ~4,000 referrals/week [SOLH-F03] volume as it grows 20% year-over-year [SOLH-F07], or if Solstice Health onboards clinics beyond today's 12 [SOLH-F01] with materially inconsistent identifier formats.

Unresolved fact that could change this choice. No target match accuracy or tolerance for false merges was given [SOLH-U01], and the expected unique-patient population size was not stated [SOLH-U06]. A false merge in a referral system risks routing one patient's PHI into another patient's specialist queue, so the acceptable false-merge rate materially affects whether deterministic rules are sufficient.

Technology options: Open-source / portable: Splink or Zingg (kept as the fallback path named in the reversal condition, runnable on Spark if adopted later). Azure-native: rule-based matching implemented in Azure SQL/Databricks SQL, or Azure Health Data Services' patient-matching capabilities where applicable. Platform-native: Azure Databricks (Spark SQL matching + Delta Lake time travel for re-processing history if rules change).

Trade-off: lower automatic match recall and more manual review load, in exchange for explainable, auditable matching the team can build and operate within the stated timeline [SOLH-F09] and skillset [SOLH-F10].

Decision 3 — Centralized Attribute-Based Access Control and Immutable Audit Logging

Chosen approach. Enforce role-based access to referral records through a single centralized attribute/tag-based access-control (ABAC) policy point in front of all referral data, paired with a centralized append-only audit log capturing every read/write, rather than implementing role checks independently inside each of the three role-based views.

Rejected alternative. Per-view role checks implemented independently inside each of the three role-based applications (referring-clinician view, specialist view, care-coordinator view), each with its own access logic and its own logging.

Why the rejected alternative is genuinely viable. With exactly three roles [SOLH-F15] and a small team [SOLH-F10], per-view checks are simpler to build first and require no additional shared infrastructure or component to operate — a real, lower-effort option under a tight 6-month timeline [SOLH-F09] and $250,000 budget [SOLH-F11].

What the chosen approach sacrifices. Additional upfront build effort and one more shared component to design, deploy, and operate before any of the three views can go live, inside the already tight 6-month timeline [SOLH-F09] and $250,000 budget [SOLH-F11] constraints.

What the chosen approach gains. A single enforcement and logging point that produces a complete, auditable access trail for every referral record [SOLH-F14], satisfying objective O3 without re-implementing (and potentially mis-implementing) the same HIPAA access rule three separate times across referring clinician, specialist, and care-coordinator views [SOLH-F15].

Reversal condition. Revisit this and simplify to per-view checks if it is confirmed that only these three roles [SOLH-F15] will ever consume referral data, no fourth consumer (e.g. a compliance dashboard or a future clinic portal) is planned, and per-view checks prove sufficient for the full 7-year audit retention requirement [SOLH-F14].

Unresolved fact that could change this choice. Whether any consumer beyond the three named roles will ever need referral-record access was not stated [SOLH-U08]; if additional consumers are already planned, the case for centralizing now (rather than later) is even stronger, and if none are ever planned, the simpler per-view alternative becomes more attractive.

Technology options (capability first, then ecosystem). The capability required is a centralized policy-enforcement and tamper-evident audit-logging layer, deployable entirely inside the contracted Azure region [SOLH-F12].
• Open-source / portable: Open Policy Agent (OPA) for the centralized policy engine, with audit events written to an append-only log store — portable if the platform is ever re-hosted within Azure.
• Azure-native (required ecosystem per constraint [SOLH-F12]): Microsoft Entra ID (role/attribute-based access) combined with Azure Monitor / Log Analytics configured as an immutable, retention-locked audit sink.
• Platform-native: Azure Databricks Unity Catalog (tag-based ABAC, row filters) if the referral data is ultimately stored and queried in a lakehouse layer.
Selection driver: the residency constraint [SOLH-F12] fixes the ecosystem to Azure; within Azure, prefer the option that gives a single, centrally auditable enforcement point rather than one embedded per application.

Trade-off: extra upfront component and build cost, in exchange for one HIPAA-compliant, auditable [SOLH-F13] [SOLH-F14] enforcement point instead of three separately implemented (and separately auditable-or-not) access checks.

Decision 4 — Intra-Region High Availability Instead of Cross-Region Failover

Chosen approach. Achieve the 99.5% [SOLH-F05] business-hours [SOLH-F06] availability target using intra-region redundancy (multiple availability zones/instances within the single contracted Azure region) only, rather than the standard cross-region active-passive or active-active failover pattern.

Rejected alternative. A cross-region failover architecture replicating the referral platform and its data to a second Azure region for disaster recovery and higher availability, following the pattern most cloud availability designs default to.

Why the rejected alternative is genuinely viable. Cross-region failover is the standard, well-documented pattern for meeting high-availability and disaster-recovery targets in Azure, and it protects against a full regional outage in a way no single-region design can. For most availability-critical systems it is the correct default, and it is not a straw man.

What the chosen approach sacrifices. Protection against a full outage of the single contracted Azure region; if that region has a significant outage during business hours, this design has no geographic fallback.

What the chosen approach gains. Compliance with the data-residency requirement that patient data must not leave the contracted Azure region [SOLH-F12], which a cross-region replica would violate by definition — this is what makes the 99.5% availability target [SOLH-F05] achievable at all without breaching the signed BAA [SOLH-F12].

Reversal condition. Revisit this if the BAA and residency agreement are amended to permit a second contracted region [SOLH-F12], or if measured intra-region availability data shows the 99.5% [SOLH-F05] target cannot be met through availability-zone redundancy alone.

Unresolved fact that could change this choice. Disaster-recovery/RTO-RPO expectations for a full regional outage were not stated [SOLH-U03], and it is not stated whether the contracted Azure region offers multiple availability zones to redound against. If the region has no availability-zone option, intra-region redundancy may be materially harder to achieve than this decision assumes.

Technology options. Azure availability zones for compute and data-tier redundancy within the single contracted region [SOLH-F12]; Azure Load Balancer / Application Gateway for zone-redundant routing; zone-redundant storage (ZRS) for the data tier. No multi-cloud or multi-region alternative is offered here because the residency constraint [SOLH-F12] rules it out directly — this is the one decision in this report where a single-vendor, single-region recommendation is justified by an explicit stated constraint rather than by default.

Trade-off: no protection against a full regional outage, in exchange for staying inside the data-residency boundary [SOLH-F12] that a cross-region design would otherwise violate.

Design Recommendations

9. Governance & Security Recommendations

HIPAA applies because referral records contain PHI [SOLH-F13], access must be restricted by role [SOLH-F15], and every access must be logged and retained for 7 years [SOLH-F14]. Governance and security therefore qualify as an ASR here (ASR 2), not an afterthought — the access and audit model must be designed before the first clinic goes live, because retrofitting it across 12 clinics' worth of live referral traffic is far more expensive than designing it in from the start.

Governance Recommendations

AreaRecommendation for this scenario
Ownership & stewardshipAssign a data owner (likely a clinical operations or compliance lead) accountable for the referral record domain across all 12 clinics [SOLH-F01].
Catalog & discoverabilityRegister the referral record schema and its sensitivity classification so future consumers (e.g. a compliance-reporting view) do not bypass the access-control layer.
Lineage & traceabilityCapture lineage from each clinic's HL7 feed [SOLH-F17] through identity matching to the final routed referral record, so an auditor can trace any record back to its source feed — directly supporting objective O3's auditable access trail [SOLH-F14].
Data contractsDefine an explicit HL7 v2 ADT ingestion contract per clinic so that a clinic's EHR upgrade does not silently break routing, especially since no clinic is willing to change EHR vendors [SOLH-F18] and the interface engine must tolerate each clinic's existing feed format.
Data qualityTreat a failed identity match or malformed HL7 message as a case for the manual review queue (Decision 2), not a silently dropped referral — a lost referral recreates the exact problem the Excel sheet caused [SOLH-F16].
Quarantine pathRoute unparseable or low-confidence referrals to a dead-letter/review queue visible to a care coordinator rather than dropping them.
Lifecycle & retentionEnforce the 7-year retention [SOLH-F08] [SOLH-F14] for both referral records and access logs as a data-lifecycle policy, with defensible deletion only after that period.
Cost governanceTrack infrastructure spend against the $250,000 first-year cap [SOLH-F11] from day one, since the budget is a hard constraint on the chosen architecture, not a target to discover later.

Access control modelUse the centralized ABAC model from Decision 3, restricting access to exactly the three stated roles [SOLH-F15] — referring clinician, receiving specialist, care coordinator.
PII/PHI protectionApply role-scoped field masking so, for example, a specialist sees only the referral fields relevant to their specialty rather than the full patient record; encrypt PHI at rest and in transit as a non-negotiable baseline.
AuditabilityLog who accessed which referral record, when, and for what action (read/write), retained for 7 years [SOLH-F14], stored separately from the referral data itself and made tamper-evident — this is what makes objective O3's "complete, auditable access trail" enforceable rather than aspirational.
Network & residency boundaryKeep all compute and storage inside the single contracted Azure region named in the BAA [SOLH-F12]; treat any component or replica that would place PHI outside that region as out of scope for this project.
Secrets & keysStore HL7-feed and database credentials in Azure Key Vault; never embed secrets in interface-engine configuration files.

Anti-Patterns to Avoid in This Design

  • Implementing the role-based view checks three separate times (once per role UI) instead of centralizing them, which is exactly what Decision 3 exists to avoid.
  • Silently dropping a referral that fails identity matching or HL7 parsing, recreating the "lost referrals" problem the Excel sheet already caused [SOLH-F16].
  • Treating the 7-year audit-log retention [SOLH-F14] as a "we'll add logging later" afterthought under the 6-month deadline pressure [SOLH-F09].
  • Provisioning any component — including a "temporary" backup or DR target — in a second Azure region or a different cloud, which would violate the residency constraint [SOLH-F12] regardless of intent.

10. Cost of Change — Where Do These Decisions Sit?

The harder a decision is to reverse, the more intentional we should be about making it.

Decision 4 (single-region deployment) sits closest to near-irreversible in practice: it is directly dictated by the signed BAA and data-residency requirement [SOLH-F12], which is itself a legal/contractual constraint, not a technical one — reversing it means renegotiating the BAA, not re-architecting software.

Governance is also near-irreversible. The centralized ABAC and audit-log model (Decision 3) becomes harder to change the more clinics and consumer views depend on it; retrofitting a different access model after all 12 clinics [SOLH-F01] are live means re-validating every role grant against 7 years [SOLH-F14] of historical access.

Lock-in note (preserve optionality). Within the mandated Azure ecosystem [SOLH-F12], prefer open, portable components where the constraint does not force an Azure-native choice — for example, an open-source interface engine (NextGen Connect/Mirth Connect) or policy engine (OPA) deployed on Azure compute keeps the option to move those specific components to another Azure service, or to a different cloud in a future project without this BAA, open. The residency constraint fixes the cloud, not every individual tool.
